# Disabled Codex transcript snapshot experiment

This internal experiment is not wired into a monitor, Stop hook, projection, or UI. It does not repair cross-session publication or change project acceptance status. It avoids retaining transcript content beyond the caller's in-memory snapshot; it creates no persistent evidence.

Before choosing a bound, five local warm Python reads plus JSON parsing of synthetic approximately 250-byte JSONL records measured medians of 4.38 ms at 0.5 MiB, 40.81 ms at 4 MiB, 163.22 ms at 16 MiB, and 931.06 ms at 64 MiB. Corresponding ranges were 3.91–4.89, 35.58–62.57, 138.17–205.22, and 662.45–1145.35 ms. These single-process cached results are not Swift, live-session, UI, p95, or concurrent performance measurements.

The experiment caps an entire source at 4 MiB. A longer session is unknown, not an empty or healthy result. This excludes potentially common long sessions; actual provider-session size distribution and incremental continuity design are not established. Do not enable this as a replacement monitor without addressing that coverage and measuring its runtime costs.

The capture uses one open descriptor for metadata and event bytes and checks identity and change information before and after reading, with a path identity recheck. Unknown includes absent or contradictory session metadata, malformed or partial records, bounded-read failure, source mutation, replacement, and oversized input. These checks cannot guarantee an atomic filesystem snapshot, detect every same-inode ABA rewrite, or prevent mutation after the final check. Provider-session metadata does not establish workspace or panel ownership; generations, restart continuity, ordered applied-result acknowledgments, attention reconciliation, old writers, and observation health remain open.

A later optimized Swift prototype measurement on the same host, five warm single-process synthetic captures, reported 0.5 MiB median 24.75 ms (24.19–25.64 ms) and just under 4 MiB median 191.76 ms (188.21–194.85 ms). A 16 MiB source returned unknown without parsing. This is not an application or p95 benchmark; repeated full scans across active sessions could be costly. The experiment rejects duplicate JSON keys structurally, including escaped-equivalent names, and bounds JSON nesting. It may conservatively reject valid input beyond these bounds.

After adding duplicate-key and nesting checks, a second optimized Swift run measured 0.5 MiB median 23.76 ms (23.26–30.55 ms) and just under 4 MiB median 188.35 ms (185.92–188.58 ms); 16 MiB returned unknown without parsing. The same limited synthetic-method caveats apply.

Opening uses a nonblocking descriptor and checks that its target is a regular file before reading. FIFO and symlink-to-FIFO inputs are rejected as unknown; a subprocess regression enforces a one-second bound for those cases. This is not a general I/O deadline: a regular file on an unresponsive filesystem can still block, and the checks do not prove a stable generation or ownership.

The parser traverses newline-delimited bytes incrementally instead of materializing a split array. It retains at most 8,192 nonblank records and at most 4 MiB of record bytes; exceeding either limit returns unknown rather than discarding evidence. Blank lines do not count as retained records. On this host, a subprocess guard for 4 MiB of metadata plus blank lines observed a 10,320 KiB peak RSS after the change using wait4 and periodic samples, versus 340,512 KiB sampled before the change. Neither figure is an application-wide memory bound. The 192 MiB guard is a regression threshold for this synthetic case, not a guarantee for all valid JSON shapes or concurrent sessions.

The deliberately failing real-CLI repro is excluded from the v1 `tests/test_*.py` discovery pattern. Run it explicitly with `BMUX_TEST_CLI="/path/to/isolated/bmux" python3 tests/codex_monitor_source_identity_repro.py -v`; its mismatch assertions are expected to fail until all relevant production consumers are fixed. It imports the fake socket from the adjacent `tests/` directory and uses temporary synthetic data. The snapshot suite runs explicitly via `./tests/test_codex_transcript_snapshot.sh`, which supplies its binary path to the separate special-file harness.
