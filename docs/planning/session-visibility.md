# Trustworthy session and turn visibility

Status: baseline investigation started 2026-11-13 on `session-visibility-baseline`, based on `origin/main` at `73994ec15`. The six dependent slices are registered in Project Truth. The baseline slice is active. PR #227 merged, and its caller-retrieval acceptance remains under observation; its unresolved caveats are preserved. No slice is accepted by this record.

## Intent and boundaries

Make ordinary Codex sessions understandable without opening transcripts: objective, meaningful work, concurrent operations, developments, next action, attention, and observation health. A turn is not a work boundary or proof of task completion. Use PE's canonical evidence, factual outcomes and SessionWorkModel, with bmux responsible for provider observation and presentation. Keep explicit agent reports, observed execution and inference distinguishable and evidence-linked. Do not join identities by time or text alone, infer stalls from silence, or let commentary clear unresolved attention. Preserve privacy and existing retention policy. This initiative does not build an orchestrator, messaging broker or knowledge compiler.

## Dependencies and gates

1. **Baseline:** trace actual ordinary CLI signals through source, ingestion, PE and native rendering; classify losses; produce representative fixtures and receipt/visible latency evidence; fix confirmed defects. Verify a real plan and status updates or identify the precise unsupported boundary. Include interruption, resume, input, concurrent operations and silence. Do not treat the limited probe below as that gate.
2. **Summary:** useful evidence-linked objective, work, concurrent activity, progress, attention and observation health in a primary surface, including unplanned sessions and restart/reconnect reconciliation.
3. **Progress:** preserve discoveries, changes and validation separately, including corrections and stale validation; compare any bounded asynchronous synthesis with a simpler baseline and prevent stale writes.
4. **Plans and reporting:** preserve explicit plan snapshots and revision uncertainty; evaluate guidance in ordinary and resumed sessions without mandatory plans for trivial work.
5. **Scanning:** validate hierarchy, accessibility and comprehension across five live sessions, including attention and observation loss.
6. **Reliability and contract:** replay and native integration acceptance, performance and cross-surface consistency; expose stable identities, relationships, evidence, revisions, capabilities, freshness and recovery ordering for future coordination.

Each gate depends on its predecessor. Existing `live_terminal_codex_evidence_ingestion`, `coding_agent_evidence_source_reconciliation`, `deterministic_turn_outcome_projection`, `session_work_model_contract_foundation`, `milestone_inference` and `blocker_approach_change_semantics` are prerequisites or reuse points, not new parallel pipelines. PE owns semantic and durable state; raw provider streams remain ephemeral under current policy. Proposed targets are p95 receipt-to-visible activity and attention within two seconds, with source-to-receipt measured separately, zero unsupported completion/cleared attention/cross-session contamination/stale overwrites, and five-session performance and reviewer comprehension measured. Change targets only with a recorded rationale before implementation.

## Newly identified prerequisite: revision integrity

Independent source review found that PE factual snapshots span multiple SQL reads, semantic publication reads and supersedes separately, and session revision uses the maximum event sequence scoped to an optional envelope session ID while projection updates use payload ownership. A payload may affect multiple sessions or move ownership. The factual turn read also joins child facts by turn ID without checking their session against the owning turn, so mismatched ownership requires explicit reconciliation rather than an assumed association. Therefore an older interpretation can replace a newer one, and comparing the existing revision alone cannot establish a coherent snapshot. These are source-level findings; a live failure has not been claimed.

The additional `session_visibility_revision_integrity` prerequisite is registered between baseline and useful-summary delivery. Its implementation must resolve inconsistent child ownership, account for prior and new direct and referenced-turn owners and replay/backfill, provide coherent cross-connection reads, and use opt-in atomic conditional publication with conflict and idempotence semantics. Preserve existing producers and historical evidence. Exercise concurrent publishers, append during reading, same-payload newer evidence, and missing/mismatched ownership. Until resolved, affected current claims must be treated conservatively; the local completed-command fix in branch `session-activity-truth` is not a freshness guarantee.

A bounded parallel correction for already answered input requests is in local branch `session-attention-resolution`, with red/green regression and focused CLI tests. It handles matching call and turn context; it does not yet establish full attention lifecycle or live native behavior. Neither local branch is merged or an accepted slice.

### Additional ordinary-session probes

A controlled ordinary bmux-hosted Codex 0.168.0 interactive session on installed bmux 0.64.17 (940) ran a silent `sleep 25`: the TUI displayed a background terminal while it ran and later showed the completed command. The transcript contained a `custom_tool_call` and final completed command, but no `item_started` for that command in this probe. PE receipt and presentation could not be measured: the installed provenance diagnostic reported no available cursor, and the installed CLI's read encountered `unsupportedSchema(found: 31, supported: 30)`. A subsequent read-only database inspection found prompt-submission events associated with that session but no command rows or command/turn lifecycle events at the time of inspection. This does not establish why the command was absent. The running app/CLI are not proven equivalent to this branch; this is a specific observed limitation, not evidence that all live paths lack starts or that the current source has a schema defect.

A further noninteractive Codex 0.168.0 probe with code mode disabled also reported the native `update_plan` tool unavailable, and the installed feature list exposed no plan-tool toggle. No supported configuration-only fix has been demonstrated. App-server schema support does not prove ordinary TUI emission; introducing an MCP reporting tool remains an unevaluated integration option, not an existing native capability or a replacement for truthful prose. Guidance, attribution, resumed sessions, and real benefit require evidence before such a tool is justified.

Revision-integrity design lead, not yet implemented or validated: reuse the existing outcome-invalidation ownership discovery where correct, extending it to prior and new referenced-turn owners and excluding unresolved cross-session child links. A per-session factual watermark with an explicit generation could be advanced transactionally for all affected owners; a conservative migration seed at the database-wide high-water mark may avoid assuming a complete retained ledger, but would not represent an exact historical session event. Use a coherent SQLite read snapshot and an explicitly negotiated conditional batch publish that validates session ownership, watermark/generation and active predecessors in the same transaction. Old clients and unrelated unconditional producers must retain their contracts; an older server must not silently accept a conditional request as unconditional. Conflicts need bounded recomputation and an unknown fallback. These choices require design review, migration and replay tests, cross-connection interleavings and measurement before adoption.

The independently reviewed local React fallback branch `session-activity-fallback` removes one presentation of completed evidence as current, but its original regression covers only a missing semantic field. The PE producer can supply an incorrect current field, and persisted semantic messages have a separate bridge. The fallback alone is not an end-to-end fix; verify realistic projected unknown, supported live activity, and message consistency before delivery.

An ordinary bmux-hosted interruption/resume probe on the same installed versions produced `turn_aborted` while the silent background command remained running; an `item_completed` for the original turn followed approximately 9.7 seconds later after stopping the command. Resuming restored the same provider session and created a new provider turn ID. The database again showed prompt association but no command records, and the diagnostics cursor was unavailable; no receipt or display latency can be inferred. A terminal turn therefore cannot by itself prove that a background operation terminated. Current importer source uses an explicit command-completion turn ID before its current context, preserving this observed attribution, but ignores `turn_aborted` and can clear the current context for an out-of-order completion of a different turn; the latter is a source-level risk rather than an observed cross-turn contamination. Source inspection also shows the current transcript monitor initializes its PE client with `try?`, which can suppress an initialization failure; whether that caused this installed-build gap is unverified. Surface that failure without exposing sensitive data, and test the actual current build before claiming the gap fixed.

A separate review of terminal-state handling found that the PE turn upsert overwrites a stored status on a later arrival. Contradictory terminal events for the same turn therefore require explicit reconciliation and evidence retention; no precedence is established by the controlled probe, which observed an abort followed by a command completion rather than a contradictory turn completion. Do not claim the broader out-of-order lifecycle gate from the scoped abort/context correction alone.

Source-confirmed plan rejection: Codex `rust-v0.168.0` rejects `update_plan` in plan mode before publishing a plan and returns `Plan updated` on the verified success path. A synthetic rejected call and matching provider rejection imported through the baseline CLI nevertheless produced one PE plan, because the importer projected arguments before reading the result. The local `session-plan-ack` branch adds a bounded, call-ID and turn-scoped acknowledgment check. Its isolated CLI rejection/wrong-turn checks and 17-test importer suite passed, including partial-line restart; the baseline CLI produced the incorrect plan in the regression. The branch is unmerged and under independent review. Its success-format support is currently limited to the verified string, unmatched/rotated/bounded-away calls remain unresolved, and already-persisted rejected plans are not repaired. The acknowledgment itself is not yet a separate PE evidence reference. These limits prevent claiming the full plan-evidence gate.

Independent review of the initial acknowledgment correction found two unresolved defects: a consumed call ID can be reused and a delayed duplicate result can falsely confirm a different call, while unresolved calls can exhaust the bounded pending set and suppress later plans. The local branch is held for correction and replay tests; its initial passing tests do not cover these cases. Acknowledgments before their calls and contradictory results also need an explicitly conservative rule.

The local `session-visibility-late-turn` branch records observed `turn_aborted` events and prevents an older turn's terminal event from clearing the newer turn context. The importer suite failed on its test-only commit, then passed all 18 tests with the fix; command completion keeps explicit turn association and is not inferred from abort. The change is unmerged and awaiting independent review. It does not resolve contradictory terminal outcomes or establish current-build native behavior.
